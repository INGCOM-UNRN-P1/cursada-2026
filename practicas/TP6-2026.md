## Reglas Generales de Entrega

1. **Encapsulamiento estricto:** Ningún archivo de cabecera (`.h`) puede
   contener la definición de un `struct`. Solo se permiten declaraciones
   adelantadas (`typedef struct fraccion fraccion_t;`).
2. **Prohibición de acceso directo:** En los archivos cliente o de prueba
   (`main.c` o `prueba.c`) está terminantemente prohibido intentar acceder a
   campos internos mediante los operadores `.` o `->`.
3. **Invariantes de representación:** Todo archivo de implementación (`.c`) debe
   contar con una función privada
   `static bool <tda>_invariante(const <tda>_t* ...)` invocada como precondición
   y/o postcondición en las primitivas públicas (mediante `assert`, validación
   defensiva o macros de contratos).
4. **Documentación Doxygen:** Todas las primitivas en los archivos `.h` deben
   estar documentadas con bloques `/** ... */` (`@brief`, `@param[in]`,
   `@param[out]`, `@return`, `@pre`, `@post`) hablando exclusivamente en
   términos de la abstracción, sin revelar detalles de la estructura interna ni
   de la implementación.
5. **Gestión de memoria:** Todas las pruebas deben ejecutarse bajo `valgrind`
   reportando `0 bytes lost` (sin fugas de memoria) y `0 errors`.

### Ejercicio 1: TDA Fracción (`fraccion_t`) — Invariantes y Normalización

Se desea modelar un TDA para operar con números racionales exactos
$\left(\frac{\text{numerador}}{\text{denominador}}\right)$.

#### 1.1. El Invariante de Representación

En `fraccion.c`, una fracción válida debe cumplir **siempre** (en todo momento
de su ciclo de vida tras ser construida) las siguientes condiciones en su
función `static bool fraccion_invariante(const fraccion_t *f)`:

1. El puntero `f` no es `NULL`.
2. El denominador es estrictamente mayor que cero ($\text{denominador} > 0$).
   _Nota: Si la fracción es negativa, el signo debe residir únicamente en el
   numerador._
3. La fracción se encuentra siempre **simplificada a su mínima expresión**
   (irreductible): el Máximo Común Divisor entre $|\text{numerador}|$ y
   $\text{denominador}$ es $1$, es decir,
   $\text{mcd}(|\text{num}|, \text{den}) == 1$. Si el numerador es $0$, el
   denominador debe ser obligatoriamente $1$.

#### 1.2. Interfaz requerida (`fraccion.h`)

Clasificar según su taxonomía y documentar con Doxygen las siguientes primitivas
en `fraccion.h`:

- **Constructor:**
  - `fraccion_t *fraccion_crear(int numerador, int denominador);`  
    Retorna `NULL` si `denominador == 0` o si falla la reserva de memoria;
    simplifica y normaliza el signo antes de retornar.
- **Selectores:**
  - `int fraccion_numerador(const fraccion_t *f);`
  - `int fraccion_denominador(const fraccion_t *f);`
- **Consultores:**
  - `bool fraccion_es_entera(const fraccion_t *f);`
  - `int fraccion_comparar(const fraccion_t *f1, const fraccion_t *f2);`  
    Retorna `< 0` si $f_1 < f_2$, `0` si son iguales, `> 0` si $f_1 > f_2$.
- **Operaciones / Constructores derivados:**
  - `fraccion_t *fraccion_sumar(const fraccion_t *f1, const fraccion_t *f2);`
  - `fraccion_t *fraccion_multiplicar(const fraccion_t *f1, const fraccion_t *f2);`
- **Conversores:**
  - `double fraccion_a_real(const fraccion_t *f);`
  - `char *fraccion_a_cadena(const fraccion_t *f);`  
    Reserva y retorna una cadena dinámica con formato `"num/den"` (ej.
    `"-3/4"`). El llamador es responsable de liberarla con `free()`.
- **Destructor:**
  - `void fraccion_destruir(fraccion_t *f);`

### Ejercicio 2: TDA Duración (`tiempo_t`) — Cambio de Implementación

Para demostrar en la práctica que la interfaz independiza al cliente de la
representación en memoria, se implementarán **dos archivos `.c` distintos** para
un mismo archivo de cabecera `tiempo.h`.

#### 2.1. Interfaz única (`tiempo.h`)

Diseñar `tiempo.h` con un tipo opaco `typedef struct tiempo tiempo_t;` y las
siguientes primitivas:

- **Constructor:**
  - `tiempo_t *tiempo_crear(unsigned int horas, unsigned int minutos, unsigned int segundos);`  
    Admite
    excesos en minutos y segundos y los normaliza: por ejemplo,
    `tiempo_crear(1, 70, 90)` equivale a 2 horas, 11 minutos y 30 segundos.
- **Selectores:**
  - `unsigned int tiempo_horas(const tiempo_t *t);`
  - `unsigned int tiempo_minutos(const tiempo_t *t);` (Rango garantizado:
    $0 \le \text{minutos} < 60$).
  - `unsigned int tiempo_segundos(const tiempo_t *t);` (Rango garantizado:
    $0 \le \text{segundos} < 60$).
- **Consultor:**
  - `unsigned long tiempo_en_segundos(const tiempo_t *t);`
- **Mutador:**
  - `void tiempo_incrementar(tiempo_t *t, unsigned int segundos_extra);`
- **Destructor:**
  - `void tiempo_destruir(tiempo_t *t);`

#### 2.2. Dos implementaciones intercambiables

1. **Implementación A (`tiempo_hms.c`):**  
   Define internamente la estructura desglosada:
   ```c
   struct tiempo {
       unsigned int horas;
       unsigned int minutos;
       unsigned int segundos;
   };
   ```
   _Invariante (`tiempo_invariante`):_
   `t != NULL && t->minutos < 60 && t->segundos < 60`.
2. **Implementación B (`tiempo_seg.c`):**  
   Define internamente la estructura compacta almacenando **únicamente el total
   acumulado en segundos**:
   ```c
   struct tiempo {
       unsigned long segundos_totales;
   };
   ```
   _Invariante (`tiempo_invariante`):_ `t != NULL`. Los selectores de horas,
   minutos y segundos calculan su valor al vuelo mediante división entera y
   módulo (`/` y `%`).

#### 2.3. Compilación y Prueba de Caja Negra (`prueba.c`)

El conjunto de pruebas en `prueba.c` incluye `"tiempo.h"` y evalúa el
comportamiento de la abstracción sin ligarse a los detalles de ninguna

El `Makefile` del ejercicio define a `tiempo_hms` como implementación primaria
y a `tiempo_seg` como alternativa:

- `make run`: ejecuta el programa demostrativo con la implementación primaria (`tiempo_hms`).
- `make run-alt` (o `make run-seg`): ejecuta el programa demostrativo con la implementación alternativa (`tiempo_seg`).
- `make test`: ejecuta automáticamente las pruebas de caja negra contra **ambas variantes** (`test-hms` y `test-seg`).
- `make test-hms`: prueba únicamente la versión primaria (`tiempo_hms`).
- `make test-alt` (o `make test-seg`): prueba únicamente la versión alternativa (`tiempo_seg`).

### Ejercicio 3: TDA Conjunto de Enteros (`conjunto_t`) — Invariante de Unicidad

Implementar un TDA que modele un **conjunto matemático finito de números
enteros** con una capacidad máxima establecida al crearse. A diferencia de un
arreglo, lista o secuencia común, en un conjunto **no existen elementos
repetidos** ni importa el orden en que fueron insertados.

#### 3.1. El Invariante de Representación

En `conjunto.c`, además de las condiciones estructurales de memoria
(`c != NULL`, puntero interno no nulo, `cardinal <= capacidad`), la función
`static bool conjunto_invariante(const conjunto_t *c)` debe verificar el
**invariante de unicidad**:

- Para todo par de índices válidos $i, j$ tales que
  $0 \le i < j < \text{cardinal}$, se cumple que
  `c->elementos[i] != c->elementos[j]`.

#### 3.2. Interfaz requerida (`conjunto.h`)

Diseñar y documentar con Doxygen las siguientes primitivas:

- **Constructor:**
  - `conjunto_t *conjunto_crear(size_t capacidad);`
- **Consultores:**
  - `size_t conjunto_cardinal(const conjunto_t *c);` (Cantidad actual de
    elementos en el conjunto).
  - `bool conjunto_esta_vacio(const conjunto_t *c);`
  - `bool conjunto_pertenece(const conjunto_t *c, int elemento);` (Devuelve
    `true` si el elemento está en el conjunto).
  - `bool conjunto_es_subconjunto(const conjunto_t *a, const conjunto_t *b);`  
    Devuelve `true` si todo elemento de `a` pertenece también a `b`, es decir,
    $A \subseteq B$.
- **Mutadores:**
  - `bool conjunto_agregar(conjunto_t *c, int elemento);`  
    Si el elemento ya pertenece al conjunto, la operación tiene éxito sin
    duplicarlo; devuelve `false` únicamente si el elemento no estaba y el
    conjunto alcanzó su capacidad máxima.
  - `bool conjunto_eliminar(conjunto_t *c, int elemento);`  
    Elimina el elemento si pertenece al conjunto manteniendo los elementos
    restantes contiguos y devuelve `true`; si no pertenece, devuelve `false`.
- **Operaciones de Conjuntos (Constructores derivados):**
  - `conjunto_t *conjunto_union(const conjunto_t *a, const conjunto_t *b);`  
    Crea y devuelve un nuevo conjunto $A \cup B$.
  - `conjunto_t *conjunto_interseccion(const conjunto_t *a, const conjunto_t *b);`  
    Crea
    y devuelve un nuevo conjunto $A \cap B$.
- **Destructor:**
  - `void conjunto_destruir(conjunto_t *c);`

#### 3.3. Desafío adicional de diseño (Opcional)

Implementar una segunda versión de `conjunto.c` donde, en lugar de administrar

### Ejercicio 4: TDA Secuencia (`secuencia_t`) — Intercambiabilidad Arreglo / Lista Enlazada

Se desea modelar un TDA general de **Secuencia lineal de enteros** que permita
acceso posicional e inserciones/eliminaciones intermedias, independizando la
interfaz pública del mecanismo de almacenamiento subyacente.

El estudiante implementará la misma interfaz `secuencia.h` en **dos
representaciones alternativas intercambiables**:

1. **Implementación sobre Arreglo Dinámico (`secuencia_arreglo.c`):**  
   Almacena los datos en un bloque contiguo en heap (`int *datos`,
   `size_t cantidad`, `size_t capacidad`).
   - _Invariante (`secuencia_invariante`):_
     `s != NULL && s->datos != NULL && s->capacidad > 0 && s->cantidad <= s->capacidad`.
2. **Implementación sobre Lista Enlazada (`secuencia_lista.c`):**  
   Almacena los datos dispersos mediante una cadena de nodos simples
   (`struct nodo { int dato; struct nodo *siguiente; };`), manteniendo el
   puntero a la cabeza, cantidad actual y capacidad límite.
   - _Invariante (`secuencia_invariante`):_
     `s != NULL && s->capacidad > 0 && s->cantidad <= s->capacidad`, y la
     longitud contada de nodos enlazados coincide con `s->cantidad`.

#### 4.1. ¿Qué es una lista enlazada?

Una **lista simplemente enlazada** es una estructura de datos lineal y dinámica
compuesta por una colección de elementos discretos denominados **nodos**. A
diferencia de un arreglo contiguo —donde todos los elementos residen en
posiciones adyacentes de memoria—, en una lista los nodos se alojan de forma
dispersa en el *heap* y se vinculan explícitamente a través de punteros.

Cada nodo está compuesto típicamente por dos partes:
1. **Dato (*payload*):** el valor útil almacenado (por ejemplo, un `int`).
2. **Puntero al siguiente nodo (`siguiente`):** la dirección de memoria del
   próximo nodo en la secuencia, o `NULL` para señalar el final de la cadena.

```text
cabeza ──> [ dato | sig ] ──> [ dato | sig ] ──> [ dato | NULL ]
```

##### Comparación conceptual: Arreglo vs. Lista Enlazada

| Criterio | Arreglo contiguo (`secuencia_arreglo`) | Lista enlazada (`secuencia_lista`) |
| :--- | :--- | :--- |
| **Disposición en memoria** | Bloque contiguo único en el heap | Nodos dispersos en el heap |
| **Acceso por índice ($k$)** | Directo: $O(1)$ por aritmética de punteros | Secuencial: $O(k)$ recorriendo desde la cabeza |
| **Inserción / Eliminación** | Requiere corrimiento de elementos en memoria | Reconexión local de punteros (tras ubicar el nodo) |
| **Sobrecosto de memoria** | Nulo por elemento (puede haber capacidad ociosa) | Un puntero extra por cada elemento (`sizeof(void*)`) |
| **Localidad de referencia** | Alta (aprovecha líneas de caché L1/L2) | Baja (saltos dispersos en memoria principal) |

<details>
<summary>🔍 <strong>Operaciones Básicas sobre Listas Enlazadas</strong></summary>

En `secuencia_lista.c`, las primitivas públicas del TDA operan internamente
sobre la cadena de nodos (`struct nodo`):

1. **Inserción al inicio (cabeza / prepend):**
   - Se reserva memoria para el nuevo nodo (`malloc(sizeof(struct nodo))`).
   - Se asigna su campo `dato`.
   - Se enlaza su puntero `siguiente` hacia la cabeza actual de la lista.
   - Se actualiza la cabeza para que apunte al nuevo nodo.
   - Complejidad temporal: $O(1)$.

2. **Inserción intermedia o al final:**
   - Se avanza un puntero auxiliar paso a paso hasta el nodo anterior a la
     posición buscada (`pos - 1`).
   - Se reserva el nuevo nodo y se asigna su dato.
   - Se conecta el `siguiente` del nuevo nodo hacia el sucesor:
     `nuevo->siguiente = anterior->siguiente`.
   - Se reconecta el nodo anterior: `anterior->siguiente = nuevo`.
   - Complejidad temporal: $O(n)$ debido a la búsqueda secuencial previa.

3. **Eliminación al inicio (cabeza):**
   - Se conserva una referencia temporal al primer nodo: `temp = cabeza`.
   - Se avanza la cabeza al siguiente nodo: `cabeza = cabeza->siguiente`.
   - Se extrae el dato y se libera la memoria del nodo desvinculado: `free(temp)`.
   - Complejidad temporal: $O(1)$.

4. **Eliminación intermedia o final:**
   - Se avanza un puntero auxiliar hasta el nodo previo (`pos - 1`).
   - Se identifica el nodo a suprimir: `objetivo = anterior->siguiente`.
   - Se saltea el nodo objetivo en la cadena:
     `anterior->siguiente = objetivo->siguiente`.
   - Se extrae el valor y se libera el nodo: `free(objetivo)`.
   - Complejidad temporal: $O(n)$ por la búsqueda secuencial.

5. **Acceso o búsqueda secuencial:**
   - Dado un índice $k$, se inicializa un puntero de recorrido en la cabeza:
     `actual = cabeza`.
   - Se avanza de forma iterativa $k$ veces: `actual = actual->siguiente`.
   - Si `actual == NULL` antes de alcanzar el paso $k$, el índice se encuentra
     fuera de rango.
   - Complejidad temporal: $O(k)$ — $O(n)$ en el peor caso.

6. **Destrucción y liberación completa:**
   - Para evitar fugas de memoria (*memory leaks*), se recorre la lista completa
     liberando cada nodo individualmente.
   - Debe resguardarse el puntero al sucesor **antes** de destruir el nodo
     actual con `free()`:
     ```c
     while (actual != NULL)
     {
         struct nodo *sig = actual->siguiente;
         free(actual);
         actual = sig;
     }
     ```
   - Complejidad temporal: $O(n)$.

</details>

<summary>📋 <strong>Reglas de Estilo Aplicables (Cátedra P1)</strong></summary>

### 1. Formato, Llaves e Indentación

- **[0x1001h](https://ingcom-unrn-p1.github.io/x1001h/)**: Indentación fija de 4
  espacios (prohibido el uso de tabuladores `\t`).
- **[0x1002h](https://ingcom-unrn-p1.github.io/x1002h/)**: Estilo Allman
  estricto para llaves: la llave de apertura `{` y la de cierre `}` se colocan
  en su propia línea, alineadas con la estructura correspondiente.
- **[0x1005h](https://ingcom-unrn-p1.github.io/x1005h/)**: Longitud máxima de
  línea de 80 columnas.

### 2. Convenciones de Nombrado

- **[0x2001h](https://ingcom-unrn-p1.github.io/x2001h/)**: Nombres de funciones
  y variables en `snake_case` minúsculo.
- **[0x2002h](https://ingcom-unrn-p1.github.io/x2002h/)**: Constantes y macros
  de preprocesador en `UPPER_SNAKE_CASE`.
- **[0x200Eh](https://ingcom-unrn-p1.github.io/x200Eh/)**: Parámetro `void`
  explícito en firmas de funciones sin argumentos.

### 3. Memoria Dinámica, Punteros y Encapsulación (TDA)

- **[0x3001h](https://ingcom-unrn-p1.github.io/x3001h/)**: Verificación
  inmediata y defensiva del resultado de `malloc`, `calloc` y `realloc`.
- **[0x3002h](https://ingcom-unrn-p1.github.io/x3002h/)**: Liberación con `free`
  y reseteo defensivo a `NULL` de los punteros liberados.
- **[0x3004h](https://ingcom-unrn-p1.github.io/x3004h/)**: Definición de tipos
  de datos abstractos mediante `typedef struct nombre nombre_t;` opaco en `.h`.
- **[0x3007h](https://ingcom-unrn-p1.github.io/x3007h/)**: Calificación
  obligatoria como `const` para punteros de entrada que no mutan sus datos.
- **[0x3008h](https://ingcom-unrn-p1.github.io/x3008h/)**: Inicialización y
  comparación de punteros nulos contra `NULL` (nunca contra `0`).
- **[0x300Bh](https://ingcom-unrn-p1.github.io/x300Bh/)**: Uso estricto de
  `sizeof` sobre el tipo o variable en asignaciones dinámicas.
- **[0x300Eh](https://ingcom-unrn-p1.github.io/x300Eh/)**: Documentación y
  gestión defensiva ante punteros nulos recibidos como parámetros.
- **[0x3010h](https://ingcom-unrn-p1.github.io/x3010h/)**: Uso del tipo `size_t`
  para longitudes, capacidades, tamaños e índices en memoria.
- **[0x3014h](https://ingcom-unrn-p1.github.io/x3014h/)**: Prohibición absoluta
  de doble liberación (_double free_).
- **[0x3015h](https://ingcom-unrn-p1.github.io/x3015h/)**: Reallocación segura:
  no sobreescribir el puntero original antes de verificar el éxito de `realloc`.
- **[0x301Bh](https://ingcom-unrn-p1.github.io/x301Bh/)**: Prohibición de
  conversiones explícitas (casts redundantes) en el retorno de `malloc` o
  `realloc`.

### 4. Compilación, Robustez y Verificación

- **[0x5002h](https://ingcom-unrn-p1.github.io/x5002h/)**: Compilación sin
  advertencias bajo `-Wall -Wextra -pedantic -std=c11 -g`.
- **[0x5003h](https://ingcom-unrn-p1.github.io/x5003h/)**: Guardas de inclusión
  canónicas (`#ifndef` / `#define` / `#endif`) en todos los archivos `.h`.
- **[0x7001h](https://ingcom-unrn-p1.github.io/x7001h/)** y

- **[0x7003h](https://ingcom-unrn-p1.github.io/x7003h/)**: Validación

- **[0x7004h](https://ingcom-unrn-p1.github.io/x7004h/)**: No llamar a `exit()`
  en funciones de biblioteca ni primitivas de TDA: propagar los errores
  limpiamente.
- **[0x7006h](https://ingcom-unrn-p1.github.io/x7006h/)**: Cobertura explícita
  de casos borde en las pruebas unitarias.
- **[0x8003h](https://ingcom-unrn-p1.github.io/x8003h/)**: Verificación completa
  con Valgrind antes de la entrega: 0 fugas de memoria y 0 errores.

## Comandos de Compilación y Prueba

- **Compilar todo el proyecto** (variantes primarias y alternativas):
  ```bash
  make all
  ```
- **Compilar exclusivamente variantes alternativas**:
  ```bash
  make alt
  ```
- **Ejecutar programas demostrativos primarios**:
  ```bash
  make run
  ```
- **Ejecutar programas demostrativos alternativos**:
  ```bash
  make run-alt
  ```
- **Ejecutar conjuntos de prueba unitarias** (evalúa automáticamente variantes primarias y alternativas):
  ```bash
  make test
  ```
- **Ejecutar pruebas exclusivamente sobre variantes alternativas**:
  ```bash
  make test-alt
  ```
- **Auditoría estricta de memoria con Valgrind** (audita ambas variantes):
  ```bash
  make memcheck
  ```
- **Auditoría de memoria exclusiva para variantes alternativas**:
  ```bash
  make memcheck-alt
  ```
- **Limpieza de ejecutables y archivos objeto**:
  ```bash
  make clean
  ```

> [!TIP] **Gestión con `tp.sh`**: Podés utilizar el script interactivo de la
> cátedra para compilar y probar módulos individuales:
>
> - `./tp.sh build` — Compila todo el repositorio.
> - `./tp.sh test` — Ejecuta las pruebas de todas las librerías y ejercicios.
> - `./tp.sh test ejercicio1` — Prueba únicamente el `ejercicio1`.
